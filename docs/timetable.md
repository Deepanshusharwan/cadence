# Personal Learning & Work Timetable

## 1. Purpose

This timetable is designed around a one-year goal:

> Build strong enough technical depth and practical experience to move toward a good product-based company (PBC).

The system needs to balance:

- A 10–6 remote job
- University/NEP syllabus that must largely be covered independently
- System Design
- DSA/problem solving
- Development skills
- Curiosity-driven/random learning
- Weekend projects
- Friends, walks, outings, and personal time
- Flexibility without falling into procrastination

The core philosophy is:

> **Fixed anchors + flexible content.**

The timetable provides hard time anchors where useful, while allowing the exact study subject/task to move around based on energy, priorities, weekly progress, and real-life events.

---

# 2. Priority Structure

## Core priorities

University and System Design have equal priority.

### Tier 1 — Core

1. **University syllabus**
2. **System Design**

### Tier 2 — Interview/problem solving

3. **DSA / Problem Solving**

### Tier 3 — Professional development

4. **Development**

This currently includes the frontend course and can later include backend, frameworks, cloud, Docker/Kubernetes, testing, etc.

### Tier 4 — Curiosity

5. **Random Learning**

This is for interesting things that are not necessarily part of the current career roadmap.

### Application

6. **Projects**

Projects are primarily a weekend activity and are where learning gets turned into practical experience.

# 3. Weekly Learning Commitments

The core weekly minimums are:

| Category | Weekly Minimum | Normal Productive Range |
|---|---:|---:|
| University | 8 hours | 9–10 hours |
| System Design | 8 hours | 9–10 hours |
| DSA | 4 hours / 4 sessions | 4–5 hours |
| Development | No hard minimum | 1–2+ hours |
| Random Learning | No minimum | As desired |
| Projects | No strict minimum | ~5–8 hours on weekends |

## Core weekly baseline

**University + System Design + DSA = 20 focused hours/week.**

The 20 hours are a **commitment**, not a ceiling.

A useful interpretation:

- **20h** → baseline successfully maintained
- **20–25h** → normal productive range
- **25h+** → bonus, not an expectation

The planner should not continually turn the higher range into a new mandatory target.

# 4. Weekday Timetable

## Standard weekday

| Time | Activity |
|---|---|
| 6:00–8:00 AM | Wake-up window + morning routine |
| 8:00–9:00 AM | DSA / Problem Solving |
| 9:00–10:00 AM | Breakfast, preparation, buffer |
| 10:00 AM–6:00 PM | **WORK — fixed** |
| 6:00–7:00 PM | Work → Study transition |
| 7:00–9:00 PM | Deep Study Block 1 |
| 9:00–9:30 PM | Dinner / break |
| 9:30–11:30 PM | Deep Study Block 2 |
| 11:30 PM onward | Wind-down / flexible personal time |

## Morning

### 6:00–8:00 AM — Wake-up window

The goal is to get up within this window rather than enforcing one exact wake time.

The morning should avoid the previous habit of spending a large amount of time lying around or doom-scrolling.

Preferred sequence:

> Wake → freshen up → breakfast/preparation → DSA

The morning should have an intentional activity early in the day.

### 8:00–9:00 AM — DSA

This is a strong daily anchor.

Default:

> **8:00–9:00 AM — DSA / Problem Solving**

The target is approximately one hour.

However, the exact timing can shift on days when waking up happens later.

For example:

> Wake at 7:30 → DSA 8:00–9:00

or:

> Wake at 8:00 → DSA 8:30–9:30

The system should adjust rather than treating a late wake-up as an automatic failure.

DSA does **not** have to happen every day. The actual commitment is:

> **4 sessions / ~4 hours per week.**

Once the weekly DSA target has been met, the planner should not force additional DSA sessions.

### 9:00–10:00 AM — Morning buffer

This is intentionally flexible.

Possible uses:

- Breakfast
- Shower/getting ready
- Personal tasks
- Preparing for work
- Starting work-related tasks early
- Small additional learning session if desired

It does not need to be filled.

---

# 5. Work Schedule

## 10:00 AM–6:00 PM — Work

This is a fixed anchor.

> **10 AM → Work starts**

> **6 PM → Work ends**

The goal is to avoid routinely pushing work into the evening and sacrificing the learning schedule.

Occasional work overruns are treated as exceptions rather than becoming the default.

---

# 6. Work → Study Transition

## 6:00–7:00 PM

This is a deliberate transition/buffer period.

It is **not mandatory leisure**.

Possible activities:

- Evening walk
- Friends
- Dinner
- Shower
- Rest
- Decompressing after work
- Personal tasks

Some days the entire hour may be used.

Other days study can start earlier/later depending on circumstances.

The purpose is to avoid going directly from:

> **10–6 work → immediate deep study**

without any mental transition.

---

# 7. Evening Study

## 7:00–9:00 PM — Deep Study Block 1

Primary categories:

- University
- System Design

The planner decides which should receive the block based on weekly progress and priority.

Example:

**Monday**
> University

**Tuesday**
> System Design

**Wednesday**
> University

The exact allocation is flexible.

## 9:00–9:30 PM — Dinner / break

A deliberate break between deep-work blocks.

## 9:30–11:30 PM — Deep Study Block 2

Primary categories:

- University
- System Design

Possible alternatives when the core targets are already healthy:

- Development
- Project-related learning
- DSA catch-up
- Random Learning

The second block remains flexible rather than forcing the same subject every evening.

---

# 8. Night / Wind-down

## 11:30 PM onward

After the main study blocks, the user can:

- Stop studying
- Relax
- Spend time with friends
- Do Development
- Do Random Learning
- Continue a project if genuinely motivated
- Wind down for sleep

However, productive late-night sessions should not routinely destroy the following day's schedule.

### Sleep targets

- **Target sleep:** 12:00–1:00 AM
- **Flexible bedtime:** 12:00–3:00 AM
- **Latest normal bedtime:** 3:00 AM
- **Wake window:** 6:00–8:00 AM

A 3 AM bedtime should not be paired with an artificially forced 6 AM wake-up.

The planner should account for the previous night's sleep when suggesting the next morning's schedule.

---

# 9. Weekend Timetable

Weekends intentionally have a different character from weekdays.

Weekdays are primarily:

> **Learn → Understand → Solve**

Weekends are primarily:

> **Build → Experiment → Consolidate → Rest**

# 11. Weekend Flexibility

The planner should support three weekend modes.

## Normal weekend

Typical goal:

- Saturday: 4–6h projects/development
- Sunday: ~2h projects + ~2h catch-up/development
- Plenty of social/free time

## Busy weekend

For outings or other commitments:

- ~2–4h meaningful work across the weekend
- Prioritize projects or core targets that are falling behind
- Do not sacrifice the entire weekend to catch up

## Full-leave weekend

For:

- Travel
- Full-day outings
- Family events
- Deliberate rest
- Other major commitments

No academic/project obligation is required when a full leave is declared.

---

# 12. Development

Development is the **career-oriented skill development** category.

Examples:

- Frontend course
- React / Next.js
- Backend development
- Django
- Docker
- Kubernetes
- Cloud
- Testing
- Frameworks
- Other practical software-development skills

The current frontend course belongs here.

## Rules

- No hard weekly minimum initially.
- Can happen during weekday flexible capacity.
- Can move to weekends when weekdays are full.
- Can be integrated with projects.
- It should not regularly displace University or System Design.

Development is intentionally lower priority than the core weekly commitments.

---

# 13. Random Learning

Random Learning is the **curiosity-driven** category.

Examples:

- Raycasting
- Compilers
- Bluetooth protocols
- Linux internals
- Research papers
- Interesting algorithms
- New programming languages
- Interesting open-source projects
- Technical rabbit holes

The key distinction:

> **Development:** intentionally learning something for professional skill development.

> **Random Learning:** learning something because it is interesting, even if it has no immediate career value.

## Rules

- No weekly minimum.
- No guilt if skipped.
- Can happen during flexible weekday time or weekends.
- Must not regularly displace core commitments.

Random Learning exists to preserve curiosity rather than turn every learning activity into a productivity obligation.

# 14. Leave System

The leave system exists to make the schedule sustainable.

## Monthly allowance

> **7 leave units per month**

Unused units can carry forward for **one additional month**.

Maximum accumulated balance:

> **14 units**

Units older than one month expire.

Leave can be scheduled in advance.

---

## Day types

| Day Type | Expected Study | Leave Cost |
|---|---:|---:|
| Normal | ~4h | 0 |
| Reduced | ~1–2h | 1 |
| Full Leave | 0h | 2 |
| Missed | Whatever happened | 0 |

### Normal Day

A normal day has an approximate target of:

> **~4 focused hours**

The weekly targets matter more than hitting exactly four hours every day.

### Reduced Day

A reduced day means:

> Something legitimately reduces the available capacity, but some meaningful learning is still possible.

Examples:

- College commitment
- Important personal/family commitment
- Poor sleep
- Unusually demanding workday
- Evening outing
- Travel preparation
- Low energy

Target:

> **~1–2 focused hours**

A reduced day consumes:

> **1 leave unit**

### Full Leave

A full leave day means:

> **No academic learning obligation.**

Examples:

- Full-day outing
- Travel
- College consuming the entire day
- Family commitment
- Deliberate recovery/rest day

A full leave day consumes:

> **2 leave units**

### Missed Day

A missed day means the planned work simply did not happen.

It is not automatically converted into leave.

For example:

> Spending several hours doom-scrolling and then deciding at night that it was a leave day does not retroactively make it leave.

This is important because the tracker should distinguish:

> **"I deliberately rested."**

from:

> **"I procrastinated and missed my plan."**

# 15. Weekly Targets vs Daily Targets

The system should prioritize weekly targets.

Core targets:

- University → 8h/week
- System Design → 8h/week
- DSA → 4h/week / 4 sessions

The daily ~4h target is a normal-day guideline.

This means one day might be:

> 2h University + 2h System Design

Another:

> 4h University

Another:

> 1h DSA + 3h System Design

The planner should care primarily about whether the weekly commitments are being maintained.

---

# 16. Planner + Tracker

The app is not just a timesheet.

It should answer:

> **What should I do?**

> **What did I do?**

> **Am I on track?**

---

## Planner

The planner generates a suggested schedule using:

- Fixed time anchors
- Weekly targets
- Priority levels
- Leave status
- Planned events
- Current weekly progress
- Remaining available study capacity
- Sleep/wake information

It should provide structure without becoming rigid.

### Example

The planner might suggest:

> 7:00–9:00 PM → University  
> 9:30–11:30 PM → System Design

But the user should be able to swap them.

The system should not treat swapping the subjects as a failure.

---

# 17. Adaptive Planning

The planner should adjust as the week progresses.

Example:

By Wednesday:

- University → 5h / 8h
- System Design → 2h / 8h
- DSA → 2h / 4h

The planner should recognize that System Design is falling behind and prioritize it in upcoming study blocks.

It should not blindly follow the original Monday schedule.

---

# 18. Priority-Based Scheduling

When available time is limited, the planner should sacrifice lower-priority activities first.

Priority order:

1. University
2. System Design
3. DSA
4. Development
5. Random Learning

Projects have their own weekend priority.

Therefore, when time is constrained:

> Random Learning → Development → DSA → University/System Design

should generally be the order in which flexible activities are reduced.

University and System Design should be protected equally.

---

# 19. Capacity-Aware Planning

The planner should recognize that not all hours have equal cognitive capacity.

For example:

After a particularly demanding workday, the planner should not insist:

> "You still owe 4 hours."

It can instead suggest:

> 45m DSA + 1h System Design

and redistribute remaining work across the week.

This is where Normal / Reduced / Leave days become useful.

---

# 20. Daily Tracking

Each learning session should ideally record:

- Category
- Start time
- End time
- Duration
- Optional task/title
- Optional notes

Example:

```text
19:00–20:30
System Design
Designing a URL Shortener
1h 30m
```

The system aggregates these sessions automatically into weekly and monthly progress.

---

# 21. Consistency Tracking

Avoid a traditional streak such as:

> "17-day streak"

because one bad day would reset the entire streak.

Instead, use rolling consistency.

Examples:

> **24/27 active days completed**

> **87% consistency**

> **University: 9/8h**

> **System Design: 7/8h**

> **DSA: 4/4h**

Planned leave should not count as a failed day.

For example:

> 24 successful days / 27 active days

is better than:

> 24 / 30 days

when three of those days were deliberate leave.

---

# 22. Weekly Review

Sunday includes a weekly review.

Example:

## Weekly Review

### Core Study

- University: 8.5 / 8h ✅
- System Design: 9 / 8h ✅
- DSA: 3.5 / 4h ⚠️

### Days

- Normal: 4
- Reduced: 1
- Full Leave: 1
- Missed: 0

### Other

- Development: 2h
- Random Learning: 1h
- Projects: 6h

### Review questions

- What went well?
- What got in the way?
- Which category fell behind?
- Was the schedule too aggressive?
- Did work consume more time than expected?
- What should change next week?

The purpose is to identify patterns rather than punish deviations.

---

# 23. Leave Does Not Create Backlogs

A critical rule:

> **Do not borrow from tomorrow.**

If Friday is a full leave day, Saturday should not automatically become a punishment day.

If 2 hours are missed, the system should not automatically create:

> "You owe 2 hours tomorrow."

Instead, the planner reassesses the remaining weekly target and redistributes work intelligently.

Small deviations should be absorbed by the weekly system.

---

# 24. Important Behavioural Rules

## Rule 1 — No doom-scrolling before starting the morning

The morning should have an intentional first activity.

The DSA block provides the first strong anchor.

## Rule 2 — Work ends at 6 PM by default

Work should not routinely consume the evening learning period.

## Rule 3 — The 6–7 PM buffer is intentional

Do not force immediate transition from work to deep study.

## Rule 4 — Weekly targets matter more than perfect days

A day does not need to be perfectly balanced.

## Rule 5 — Leave is deliberate

Use leave when you genuinely need time away from learning commitments.

## Rule 6 — Reduced days consume leave

This prevents reduced days from silently becoming the default.

## Rule 7 — Development and Random Learning are flexible

They should not create guilt or compete with core commitments.

## Rule 8 — Weekends are for building and recovery

Projects are important, but the weekend should not become another 10–6 workweek.

## Rule 9 — Do not optimize for maximum hours

The goal is sustainable progress over one year.

## Rule 10 — The planner supports flexibility

The schedule should guide behaviour without becoming a rigid prison.

# 26. Core Principle

The system should optimize for:

> **Consistency over intensity.**

The goal is not to recreate the 12–16 hour study days from the past.

The goal is to create a system that can survive:

- A normal workday
- A bad day
- A busy week
- College
- Outings
- Social life
- Low motivation
- High motivation
- Unexpected work
- Weekends away

and still keep the one-year trajectory moving forward.

The timetable therefore combines:

> **Hard anchors + weekly commitments + flexible scheduling + deliberate leave + adaptive planning.**

That is the foundation of the timetable and the planner/tracker app.
